# SPEC: 153 — INBOUND_MULTI_CERTIFICATE_SNI

| Поле | Значение |
|------|----------|
| Тип | F — несколько сертификатов на TLS inbound с fallback по порядку списка |
| Статус | O (open) |
| Ветка | `lx` |
| Build-tag | — |

## 1. Проблема

Inbound принимает только одну пару сертификат/ключ. Сертификат на несколько несвязанных имён раскрывает их все независимо от SNI. ShadowVPN2 должен передавать в один inbound отдельные сертификаты для каждого имени, чтобы TLS выбрал совпадающий.

## 2. Контракт

`tls.certificates` — упорядоченный список записей сертификатов. Каждая запись содержит один источник сертификата и соответствующий источник ключа: inline (`certificate`, `key`) либо файлы (`certificate_path`, `key_path`). Первый сертификат используется по умолчанию при отсутствующем или неизвестном SNI и для ClientHello, алгоритм подписи которого не поддерживает более поздние сертификаты. Для известного SNI Go `crypto/tls` выбирает совместимый сертификат, SAN которого соответствует имени.

 Одиночные поля inbound-сертификата остаются поддержаны загрузчиком для совместимости, но исключены из генерируемой схемы; ShadowVPN2 выдаёт только новый список `certificates`. Нельзя задавать одиночные и множественные поля одновременно. Пустой список, неполная пара или смешанные источники — ошибка.

Пути сертификатов отслеживаются. Изменение атомарно перезагружает упорядоченный набор; некорректная замена сохраняет активный набор. TCP и QUIC используют одинаковую логику `tls.Config`. Reality остаётся несовместимым с обычными сертификатами.

## 3. Fallback

 Отдельное fallback-имя не нужно. Первый элемент списка — явный fallback. ShadowVPN2 ставит сертификат домена ноды первым. Для неизвестного/отсутствующего SNI Go `crypto/tls` выбирает первый сертификат, совместимый с алгоритмами подписи клиента.

## 4. Контракт ShadowVPN2

`InboundTlsConfig` сериализует упорядоченный список объектов сертификат/ключ в `certificates`. Contributors ставят сначала сертификат настроенного домена протокола, затем остальные managed-сертификаты в стабильном порядке по домену, исключая дубли по идентичности сертификата. При отсутствии managed-сертификата используется единственная настроенная self-signed пара. `server_name` остаётся ожидаемым доменом протокола и не выбирает серверный сертификат.

Хранение и ACME-выпуск managed-сертификатов выполняются по одному домену. Существующий per-node multi-domain документ заменяется документами node/domain. Старые multi-SAN сертификаты после изменения не выдаются; выполняется выпуск отдельных сертификатов для желаемых доменов. Повторное использование допустимо лишь для сертификата, покрывающего ровно целевой домен.

## 5. Тесты и критерии приёмки

- Два разных сертификата: совпавший SNI получает соответствующий leaf; неизвестный и отсутствующий SNI получают первый сертификат.
- Для несовместимых signature algorithms выбирается первый совместимый сертификат по правилам Go TLS.
- Некорректная/неполная запись приводит к ошибке конфигурации.
- Перезагрузка файлов атомарна; некорректный файл не заменяет активный набор.
- Naive TCP и Hysteria2 QUIC получают один и тот же упорядоченный набор.
- ACME заказывает каждый домен отдельно; ShadowVPN2 сохраняет каждый отдельно; node-domain идёт первым; старый multi-SAN сертификат не попадает в generated config.
- `sing-box check` принимает конфигурацию; TLS loopback smoke проверяет известный, неизвестный и отсутствующий SNI.

## 6. Границы

 Одиночные поля inbound-сертификата остаются поддержаны загрузчиком для совместимости, но исключены из генерируемой схемы. Нет нового certificate provider. Не меняются клиентский TLS, клиентские сертификаты, ECH и Reality. Выбор fallback домена ноды фиксирует поведение и не выдаёт сертификат со всеми настроенными доменами; это не является заявлением о снижении обнаруживаемости активным пробингом.
